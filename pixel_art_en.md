# From 3D to Pixel Art: Inspiration, How It Works, Process

> This covers only the mechanism behind Midi Runner's look, so it can be reused in other projects. Written 2026-11-19. Every number was checked against the code and `config/tuning.csv`. Sources are given in brackets, relative to the project root.
> tuning.csv overrides the scripts' defaults at run time; where the two differ, the CSV wins. For how levels are generated from music, see [process_en.md](process_en.md).

---

## 1. Inspiration

### 1.1 Why "build the world in 3D + a pixel post-process"

The levels are generated from music data (see [process_en.md](process_en.md)), so every level's terrain, mechanics and background are different and can't be drawn in advance. The visuals have to be generated by code too.

- **Build in 3D**: blocks, pillars and shapes are easy to generate in code, and perspective, parallax, depth and lighting come for free.
- **Turn it into pixel art with one full-screen post-process at the end**: however each thing is generated, it ends up unified by the same pixel grid, the same brightness steps and the same outlines, so it reads as one hand-made piece of pixel art.
- The result: the game has **no hand-drawn texture**. The only outside art asset is the pixel font Upheaval (Brian Kent, freeware).

### 1.2 Visual references

- **A music player's spectrum bars**: the ground is rows of square pillars rising and falling with the music.
- **A piano roll / MIDI editor**: notes are blocks laid out sideways, and their height is their pitch.
- The "music as geometry" feel of **音律创想 (ODDADA)**: one shape per instrument.
- **The texture of old games**: only 16 brightness steps, gradients dithered into dots, night stars updated only 15 times a second.

## 2. How it works

### 2.1 The pixel post-process: one full-screen shader does it all

`shaders/pixel_post.gdshader`, driven by `scripts/view/pixel_post.gd`. It is a full-screen ColorRect on CanvasLayer 0, over the 3D picture and under the HUD, so text isn't pixelated. In the development build F2 toggles it to compare with the raw picture.

**Cell size.** The screen's height decides how many screen pixels a cell takes. The result is a whole number, so every cell is square (`:48`):

```
screen pixels per cell px = max(1, floor(screen height / 270 + 0.5))      # 270 = PIXEL_ART_H
```

| Window height | Screen pixels per cell | Rows of cells on screen |
|---|---|---|
| 648 | 2 × 2 | 324 |
| 720 | 3 × 3 | 240 |
| 1080 | 4 × 4 | 270 |
| 1440 | 5 × 5 | 288 |
| 2160 | 8 × 8 | 270 |

**What happens to each cell, in order:**

1. **Sample**: take the colour at the cell's centre, nearest-neighbour (`cell_rgb`, :37-44).
2. **Boost colour**: saturation × 1.15, contrast × 1.05 (`PIXEL_SAT`, `PIXEL_CONTRAST`). Pixelation eats some colour, so this puts it back first.
3. **Find edges, darken them**:
   - Compare brightness with the 4 neighbouring cells; a difference over 0.14 counts as an edge (`PIXEL_EDGE`, smoothstep 0.14→0.16, almost a hard edge).
   - The darker side gets 40% darker (`PIXEL_OUTLINE 0.4`). The lighter side gets no highlight (`PIXEL_HIGHLIGHT 0`).
   - Where both sides keep brightening or darkening the same way, it is a **gradient**, not an edge, and gets no outline (:61-62). So a pillar's shading isn't traced with a line.
4. **Quantise in YCoCg colour space**: brightness Y keeps only **16 steps**, chroma Co and Cg **64 steps** each (`PIXEL_LEVELS`, `PIXEL_CHROMA`, :71-80). Coarse brightness, fine colour: retro steps of light and dark, with hues kept close to the original.
5. **Dither**: 4×4 Bayer ordered dither at strength 0.8, only where a gradient is detected (`PIXEL_DITHER`, :74-77). The pattern is indexed by cell, so it sits on the pixel grid. Flat faces stay one solid colour; gradients become fields of dots instead of colour bands.

**The grid is pinned to the run.** The camera scrolls every frame. A grid fixed to the screen would make whole areas flicker every time something moved half a cell.

- Every frame, the screen position of the world point `ANCHOR (0, 0, 0.5)` is computed and the whole grid aligned to it (`pixel_post.gd:11, 72, 85-88`). That point is at the depth of the pillars' and the hero's front faces.
- It reads the camera's physics-interpolated position (`get_global_transform_interpolated`, physics at 120 Hz), the same position the picture is drawn from; otherwise the grid would drift off the picture.
- The cells on those front faces move with the run and don't flicker. Far layers aren't at that depth and slide slightly, but they are low-contrast background anyway.

**Full-screen flash (`pulse`).** The same node also tints the whole screen: a second full-screen ColorRect whose opacity fades linearly over 0.22 s (`PULSE_T`). On PERFECT it shifts 0.2 toward gold with a 0.1 camera jolt; on a successful flip it shifts 0.16 toward the mechanic colour.

### 2.2 Scale: decide the smallest detail first, then the cell and the camera

All the scales follow from one rule: **any detail meant to be seen takes at least 2–3 cells**. Anything smaller turns to mush once pixelated.

| What | Value | Source |
|---|---|---|
| Camera | perspective, 50° vertical FOV; 15 m in front of the run and 2.6 m above the hero, looking at a point 4.5 m ahead of the hero and 0.6 m above the ground | `scripts/view/camera_rig.gd:7-11` |
| Which gives | about 7.6° looking down, about 14.1 m visible height at the run, **1 cell ≈ 0.052 m** (1080p) | — |
| Mechanic voxel | 0.15 m ≈ **2.9 cells** | `scripts/view/voxel_column.gd:13` |
| Hero | 0.72 × 1.4 m ≈ **14 × 27 cells**, corner radius 0.17 m | `scripts/view/player_look.gd:84` |
| Hero's voxel form | 4 × 8 × 4 cubes of 0.175 m, each about 3.3 cells | `player_look.gd:24-27` |
| Ground pillars | 1.4 m apart, filling 80%, half-width 0.35–0.6 m | `scripts/view/pillars.gd:14-16` |

- **Look and hit box are separate**: the jelly squash, dash lunge and flip only change the look, never the hit box (`player_look.gd:16`).
- **Voxel counts are rounded**, so every column is a whole number of voxels (`voxel_column.gd:85-90`).
- The camera sits 4.5 m ahead of the hero, so anything in front of the hero (closer to the camera) overlaps it unless kept about 0.25 m clear.

### 2.3 Colour rules

**One theme colour per level**; every pillar's gradient uses it (tuning.csv:6). Midi Runner's five levels are orange `#ff801f`, teal `#1ac7b8`, purple `#9e4dff`, blue `#4d80ff` and rose `#ff4f8b`.

**The mechanic colour is the theme's opposite hue, kept for things the player interacts with.** This is the single most important rule of the look.

- How: hue + 0.5, with saturation and value tuned per level (`ACCENT_S`, `ACCENT_V`; level.gd:143-145, 1240-1243).
- In the mechanic colour: everything to dash through, step on, dodge or hold.
- The background only shifts hue around the theme colour and is always less saturated than the mechanic colour (`BG_HIT_SAT 0.6`); denser layers fade more.
- The few exceptions (golden stars, green springs, red / blue / yellow for three kinds of drum) are all told apart by **shape** too.

**Hard readability rules** (measured on renders):

| Rule | Why |
|---|---|
| Interactive things differ from the sky by ≥ 0.2 in brightness | visible at a glance even under a pale sky |
| A brightness change needs at least +0.15 to show | each of the 16 steps is about 0.11–0.15; anything smaller is quantised away |
| Kinds are told apart by shape, not only colour | quantising and dithering eat small colour differences |
| Far column tops match the sky's brightness (\|ΔY\| ≤ 0.15) | only their hue shows, so they never compete with the foreground |

**The sky changes warm / cool with the chords.** The background is a flat colour, no skybox. Back to the home chord it turns warm (0.98, 0.87, 0.74); away from it, cool (0.72, 0.81, 0.98); ambient light and sunlight change with it (`camera_rig.gd:15-16, 33-36, 64-71`).

### 2.4 Shape language: one shape per sound

Every MIDI note in the background is a small shape, and **each instrument has its own shape** (`midi_background.gd:17-24`):

| Part | Shape | Depth (metres, × 1.5) |
|---|---|---|
| Lead | ring | −7 |
| Arpeggio | ball | −13 |
| Hi-hat / clap / kick | small cube / tetrahedron / octahedron | −19 |
| Bass | long capsule | −30 |

- Tetrahedra and octahedra are flat-shaded, so after pixelation each face is one solid colour, which suits pixel art.
- Foreground mechanics are all **square**; background shapes are all **round or pointed**. At a glance the player can tell "what I have to deal with" from "what is just playing".

### 2.5 The whole picture moves with the music

**The hero is the playhead**: each note is placed where the hero is at the moment it sounds, so whichever note the hero reaches is the one sounding (`midi_background.gd:3-4`).

| Element | How it moves | Source |
|---|---|---|
| Background notes | light up and swell when they sound, decaying as exp(−age × 6) (drums × 8); a glow before the note; clearer and spinning faster during the climax | `shaders/midi_note.gdshader` |
| Spectrum pillars | each follows one band's live level; 7 to a group, lows in the middle and highs at the edges, swelling like a spectrum | `pillars.gd:3-7` |
| Mechanic pillars | pump with the lows; the climax stretch glows and every kick flashes the tops | `pillars.gd:20-21, 140` |
| Far waves | three rows of thin columns, each the song's average loudness over 0.25 s, forming a "skyline"; multiplied every frame by one band's live level, stretching on kicks | `scripts/view/far_waves.gd` |
| Phrase starts | the whole background pulses; the ground alternates light and dark, like piano keys | `midi_background.gd:152-169`, `pillars.gd:227-235` |
| Hold mechanics | the ribbon's stripes flow back; the last beat brightens 50% to signal letting go | `shaders/ribbon.gdshader:15-30` |

### 2.6 Building blocks generated in code

**Pillars** (BoxMesh + `shaders/pillar.gdshader`):

- Colour, glow and gradient start are instance uniforms, so hundreds of pillars share one material.
- From the top down, the body fades from the light colour to a dark one (theme colour × 0.12) over 5 m with a squared falloff; the top is lightened 15–50% toward white.
- Every pillar reaches a dark floor at −60 m, so looking down from a pit you never see the bottom.

**Voxel columns: the building block every mechanic shares** (`scripts/view/voxel_column.gd` + `shaders/jaw_voxel.gdshader`):

- Each size gets one MultiMesh, and every mechanic of that size shares one material.
- Within 0.6 m of the working end it is solid; beyond that only the front and the two sides are built.
- Each voxel's brightness jitters ±0.14: after pixelation this gives a slight hand-made grain instead of a dead flat colour.
- The top voxel at the working end glows × 2: the end the player has to hit is the brightest.
- **Breaking is computed entirely on the GPU**: a ballistic arc (gravity 22), one bounce then a 0.25 s slide, a random spin per voxel, shrinking away over the last 0.3 s, a flash as it breaks. The shader computes each position straight from "the moment it broke + a random seed"; the CPU only records when it broke.

**The hero: a jelly block**:

- The mesh is a rounded box generated in code, with a 6 × 6 grid per face, enough vertices for the deformation.
- The jelly deformation runs in the vertex shader: it squashes or stretches vertically from the feet, with the width changing the opposite way to keep its volume; the spring runs at 7 Hz with a maximum deformation of 0.28 (`shaders/jelly.gdshaderinc`, `player.gd:25-30`).
- The outline is an inverted hull pushed out 0.05 m, in a dark version of the body's hue; with the post-process's automatic dark edges on top, it has a clear outline on any background.
- Its colour = the block under its feet moved 45% toward the theme colour and lightened 35%, kept at least 0.25 in brightness away from that block, so it never blends into what it stands on.
- On a failure it bursts into 4 × 8 × 4 voxels, which fly back and reassemble within 0.3 s on respawn.

**2D elements are pixel art too**:

- The transition, the record and the 2D hero are SDFs (signed distance fields) in shaders, **sampled at cell centres**, so their edges are naturally stepped cell by cell. The transition is a hole shaped like the hero.
- The hand on the key sign, the intro panel's icons and sprites: pixel images written line by line as strings (for example `"..oooo.."`), drawn at whole multiples at run time (`scripts/view/key_sign.gd:18-29`, `intro_panel.gd:26-129`).
- Night stars: only 5 brightness steps, updated only 15 times a second (dropped frames on purpose), scattered at random with a minimum gap, avoiding the text areas (`scripts/view/night_stars.gd`).
- The icon: a 256 × 256 SVG made only of rectangles aligned to 4 px, really a 64 × 64 piece of pixel art, exported only at whole multiples.

### 2.7 UI alignment: the font is the only ruler

- The pixel font Upheaval's native size is **20 px**, where each stroke is exactly 1 screen pixel. All text on screen uses only whole multiples of 20 (`hud.gd:12`).
- **Canvas snapping** (`_snap_canvas`, hud.gd:111-122): the layout is designed at 1152 × 648; when the window is bigger, a canvas size is chosen so that 20 screen pixels are a whole number of canvas units. 1920 × 1080 and 2560 × 1440 stay exactly 1152 × 648.
- **Rounding font sizes** (`fit`, hud.gd:81-96): k = round(design size × scale / 20), clamped to each label's own range; font size = k × 20 ÷ scale.
- **Outlines** (`outline_for`, hud.gd:103-104): 2 font pixels wide; text smaller than 30 uses 4 when scaled up, or it looks hollow.
- The font has antialiasing, hinting, subpixel positioning and mipmaps off, sampled nearest-neighbour.
- Pixel cells for menus and transitions: `clampi(floor(window height / 270), 2, 8)` screen pixels each, the same size as the 3D picture's cells at 1080p.

## 3. Process

### 3.1 Steps to set this look up in a new project

1. **Build the world in 3D first**: blocks, pillars, shapes, flat colours, no textures.
2. **Decide the smallest detail**: how big (in metres) the smallest thing that must be seen is, and how far away the camera is.
3. **Set the cell size from that**: the smallest detail takes 2–3 cells. Midi Runner has 0.15 m voxels, 0.052 m cells and a 270-cell-high picture.
4. **Add the pixel post-process**: take `pixel_post.gdshader` + `pixel_post.gd`, over the 3D and under the HUD.
5. **Pin the grid to the main depth**: pick a world point as the anchor, on the layer of the player's and main objects' front faces.
6. **Set colour rules**: one theme colour, its opposite hue only for interactive things; the background always less saturated than that.
7. **Check on renders**: use the hard rules in 2.3, measured on the actual rendered pixels.
8. **Look at two window sizes**: at least 1152 × 648 and 1080p (or 1728 × 972). Text and panels that look right at one size can be all wrong at another.
9. **Web build**: add every material to the warm-up list (3.3).

### 3.2 Pitfalls we hit

| Pitfall | Cause | Fix |
|---|---|---|
| A brightness change doesn't show | 16-step quantisation swallows anything under one step | change brightness by at least +0.15 |
| High saturation set, but it looks pale on screen | tonemapping and glow leave bright tops with about half their set saturation | let bright tops carry hue only, not saturation |
| Measuring colour at one point gives the wrong answer | cells, dither and outlines mean one point doesn't stand for the whole | measure on full renders, over each object's real projected area |
| A corner-to-corner box mask read column tops as sky | the camera looks down, so columns are slanted in the picture | mask with each column's projected front and top faces, using the interpolated camera position |
| A panel was "all black" in the editor's 1152×648 window | it was 3% wider than the window, and reviews had only looked at 720p and 1080p | check at both sizes every time |
| Text blurry with lost outlines on the web and in the 1080p video | Godot builds a font at size × scale, with the scale cut to 1/64 and the outline to whole pixels; at a scale of 1.5–1.67, 1× text loses its outline | canvas snapping + `outline_for`; small text doubles its outline when scaled up |
| `outline_size = 0` set, but the outline is still there | LabelSettings' outline colour defaults to white, and a refit sets the size back | set the outline colour fully transparent |
| Web build colours are off | the Compatibility renderer has a different colour path, and `scaling_3d_scale` below 1 takes yet another | its own `compat_gamma` / `compat_gain`; don't lower `scaling_3d_scale` |
| Settings lost after a material swap on the web | under Compatibility each object's settings live in its own material copy, so swapping `material_override` drops them | set them again right after the swap |
| The web build's first open took about 22.8 s | every material first compiles a default variant that is never used | give those variants an empty shader through `html/head_include` in the export settings: down to about 3.5 s |

### 3.3 Web warm-up

The web build uses the Compatibility renderer (WebGL2). Every new material has to compile its shader the first time it is drawn, which causes a hitch.

- `scripts/view/warm_up.gd`: on the loading screen, every material combination is drawn once in advance. Midi Runner has 9 kinds: `lit`, `glowing`, `floor_mat`, `fading`, `flat`, `flat_glow`, `see_through`, `beam`, `holes` (warm_up.gd:180-205).
- **Any new kind of material must also be added to this list**, or the web build will hitch the first time it draws it.

### 3.4 How to tune it

Every setting of the look is in `config/tuning.csv`, with a Chinese note in the second column of each row:

| To change | Edit this row |
|---|---|
| Cell size | `PIXEL_ART_H` (smaller = bigger cells) |
| How retro | `PIXEL_LEVELS` (fewer = more retro) |
| Colour bands / dots | `PIXEL_DITHER` |
| Outline strength | `PIXEL_OUTLINE`, `PIXEL_EDGE` |
| Theme colour | `theme_color` |
| Mechanic colour saturation and brightness | `ACCENT_S`, `ACCENT_V` |
| How much the background fades | `BG_FADE`, `BG_HAZE`, `FAR_HAZE` |
| Menu colours | `MENU_BG`, `MENU_INK` |

Running in the editor, **F2** toggles the pixel post-process for a direct comparison.
